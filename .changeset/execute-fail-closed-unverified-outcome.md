`trade execute`: never treat an unverified broadcast as "nothing was sent". Once a signed payload has been handed to a wallet or the execute API, an unreadable response, network failure, HTTP error, WalletConnect failure, receipt timeout, or confirmed on-chain revert now stops the command and marks the quote as spent instead of signing the next candidate. HTTP status alone—including 400, 408, 409, and 429—no longer claims that the backend rejected the transaction before broadcast. Execute responses must carry a documented `Success` or `Failed` status; missing or unknown statuses fail closed. Solana success responses must contain a transaction signature or hash, and gasless EVM success responses must contain the solver transaction hash; otherwise the outcome fails closed instead of printing a successful transaction with an unusable identifier. The same protection covers WalletConnect swap, approval, and allowance-revoke sends, mismatched hashes, malformed success responses, and application-level failure responses that still contain a transaction identifier. Quotes also remain claimed after post-broadcast approval or revoke verification failures, preventing reuse while the allowance state is unknown.
