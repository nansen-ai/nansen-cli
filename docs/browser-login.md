# Browser login prerelease

Browser sessions need coordinated server admission, account permissions and revocation enforcement before cohort rollout. Cross-service parity and staging acceptance remain required. Automatic renewal and normal-release promotion ship separately.

## Commands and selection

Plain `nansen login` always requests fresh approval, including when an environment key or saved credential exists. `--no-browser` skips automatic opening only. Email/password and Google are the upstream consent methods; Apple is not advertised. The browser owns explicit account/client/code/access consent. Visiting the URL alone does not approve.

Ordinary commands select an existing supported explicit override, then NANSEN_API_KEY, then one saved credential. There is no new global key option and no named profile. An empty selected key is an error. Saved authentication can be a legacy key or browser session. The new `config.json.auth` pointer also represents a deliberate logout, so an old development config key cannot silently reappear. Existing direct API-key commands continue to work. Legacy explicit `--human`/`--api-key` setup retains option, environment, then hidden-prompt precedence. Plain login no longer copies an environment key to config.

Candidate B is checked independently through GET `/api/v1/account` with only its Bearer token. Environment A cannot mask a rejected B. This check is free and permits zero research credits. An environment override remains in force after B is saved; unset it to use B. Data commands never launch consent. Until API507, expired sessions return a login instruction. A service outage stays transient, not a reason to change accounts.

Selected credentials never trigger automatic x402 signing. Anonymous automatic payment and explicit manual Payment-Signature with an API key retain their existing behavior. Browser Bearer requests cannot include an API key or payment signature. The resource contract uses Bearer without DPoP; a copied valid access token is accepted by that policy. Proof of key possession applies to authorize/poll/revoke, not API requests. First-party device pairing requests `nansen:api`, granting the same account API permissions as an API key, including smart-alert CRUD and existing trade API operations, subject to plan, account and endpoint checks. Existing `nansen:read` OAuth/MCP grants are not upgraded; old read-scoped CLI sessions require fresh login. Hosted simulation resolves the selected credential through the shared auth owner and sends it only to the matching trusted API origin. Custom third-party RPCs receive no Nansen credential. Wallet signing still requires a separately configured wallet. MCP installation exports a long-lived integration key into another client and therefore requires an API key; a short-lived audience-bound browser session is not an exportable key. This separate integration setup requirement does not reduce browser-session permissions on the account API.

## Machine output

`login --json` and non-TTY login emit NDJSON. There is one pending event and one terminal event on a normal approval attempt. Preflight failure emits only the terminal error. Human progress goes to stderr in machine mode.

```json
{"version":1,"event":"pending","verification_uri":"https://idp.nansen.ai/device?user_code=ABCD-EFGH","user_code":"ABCD-EFGH","expires_at":"2026-09-19T00:10:00.000Z"}
{"version":1,"event":"saved","account_id":"example-account","effective_source":"session","cleanup":[]}
```

Failure/cancellation events contain a fixed code, message and cleanup outcomes. Events never contain device_code, access/refresh token, private JWK, proof or nonce. Public user codes are displayed only for approval, never telemetry. Local diagnostics are cached/unverified; the native store is not opened by status because it could prompt. `storage_access:not_checked_no_prompt` is deliberate, not a success claim.

## Custody and coordination

Optional, pinned dependencies are `@napi-rs/keyring@2.1.0` and `fs-native-extensions@1.5.1`. Help, offline metadata and environment/explicit API-key requests do not need native bindings. Saving/removing auth requires the lock binding; browser pairing also requires secure storage. Reinstall with optional dependencies if a binding is absent. No plaintext, wallet-password-file or Linux keyutils fallback exists.

The browser session's private ES256 JWK, refresh token and access cache live only in `nansen-cli-api-auth-v1` OS entries. Native operations run in bounded child processes; secret input/output travels through private pipes. Helpers receive no secret argv or inherited API-key environment. Before receiving operation or credential data, the helper independently acquires the stable `auth-store.lock` execution gate inside the same authentication directory. Every read/delete uses this same gate, so recovery cannot overtake a helper whose parent died. The gate is subordinate to the existing auth-state owner, not an alternate writer protocol; it is never unlinked. Successful operations await helper termination before releasing a writer's lock. If termination is not observed within one second of the ten-second kill deadline, the caller fails instead of waiting indefinitely; the helper-owned gate still protects cleanup, which must retain the journal if the helper survives. Synchronous keyring calls execute on a worker thread inside that guarded process. Its main thread keeps the parent pipe open and force-terminates the entire process on parent EOF or its own ten-second watchdog, including when the native thread is blocked. A result is returned only after that thread exits. An externally stopped process cannot run its watchdog, but retains exclusion: recovery fails bounded, reports deletion incomplete and retains its journal until that process dies. No age-based lock stealing or blind cleanup success is allowed. The CLI uses ordinary Entry construction, not the Windows withTarget constructor that can create an empty placeholder.

The UTF-8 bundle has an explicit 16 KiB client compatibility limit. It is split into at most eight 2,048-byte entries plus a bounded manifest with byte length, chunk count and SHA-256 digest. The manifest and every chunk belong to one immutable random generation. This respects the documented Windows 2,560-byte blob limit using the binding's byte setter, without assuming an entire JWT/key bundle fits one entry. Missing/mixed/corrupt chunks fail closed. Runtime byte length and readback are checked before selection. Larger issuance fails without replacing the prior credential.

Linux explicitly selects persistent Secret Service over the user's D-Bus session. macOS uses Keychain. Windows uses Credential Manager with the binding's default Enterprise persistence, which can roam according to OS policy; it is not promised device-local-only. Windows cohort support still requires native verification and any required Local-persistence adapter. Remote shells need a usable unlocked store; a kernel keyring or a headless process without Secret Service is not an equivalent fallback.

A stable, never-replaced `auth.lock` uses an OS advisory lock and same-process serialization. No lock is stolen because of its age. Only local filesystems are intended; network/synchronized home directories are unverified. Login snapshots selectionEpoch before approval, releases the global lock while waiting, then compares that epoch before installation. Login/key replacement/logout changes the epoch; future refresh changes only secret generation. An earlier pending login cannot overwrite a later committed choice or logout.

All saved-auth writes use auth-state. The same-directory atomic config replacement preserves unrelated settings, removes a superseded saved key, and selects a complete secure generation. Legacy explicit API keys retain their existing config-file storage policy. Nonsecret bounded journals list only operation/generation IDs for targeted recovery, never credentials. Live attempts hold separate OS locks. Recovery skips active generations and live attempts, cleans interrupted unreachable generations, and never restores a superseded credential. A lost commit acknowledgement rereads the pointer before cleanup. If the pointer cannot be classified safely, leave cleanup pending rather than revoke a possibly active session.

Process interruption and filesystem power loss differ. Unit/child tests demonstrate process-fault recovery under the tested filesystem semantics. Native storage readback and POSIX file/directory fsync do not prove all-OS power-loss durability. Windows replacement/durability, store blocking behavior and cross-login persistence remain verification gates.

## Logout and uncertainty

Logout advances the epoch and leaves a tombstone before retiring/deleting the prior session. It preserves wallets, wallet password entries and environment keys. A locked store can permit clearing selection but prevent physical deletion; the CLI reports deletion incomplete. Unlock the OS store and rerun logout. Successful local deletion with offline/rejected retirement is reported separately as remote revocation unconfirmed. Review the old CLI device using the account's supported security controls if cleanup cannot be confirmed.

`POST /token/revoke` uses the old refresh token and its own key, without requiring live access. A protected receipt means family retirement recorded with API propagation pending; it is not immediate gateway rejection. The consumer separately bounds cached revocation data by both receipt age and source age, with explicitly configured age plus future-skew bounded by the configured stale window and 300 seconds. Those are engineering ceilings, not an accepted deployment propagation policy; the CLI does not turn a receipt into an immediate-rejection or fixed-delay promise. A legacy refresh-only receipt means already-issued access can survive until expiry. Other devices and independently managed API keys are not revoked.

If the server consumes approval but token issuance then fails, a later poll can report that the code expired or was consumed. The CLI tells you to run `nansen login` again; it does not restart pairing automatically or claim the failed attempt issued no tokens. Start a new login and approve the new code.

There is an unavoidable crash window after issuance but before durable custody. A lost issuance response or killed process can leave a family for which this CLI lacks cleanup authority. Device codes are single-use; replay is not a recovery protocol. Pre-issuance cancellation stops polling and allows the grant to expire, since there is no CLI cancel endpoint. API507 must separately implement persisted rotation-in-flight handling for a lost refresh response; this draft has no refresh engine. Its implementation must extend this same `auth-state.js` owner: acquire `auth.lock`, reread epoch/generation, persist a nonsecret rotation marker before transmitting, hold the lock through the bounded request and durable generation switch, then clean the displaced generation. Logout/replacement wait for that owner, advance the epoch, and can never be undone by a stale refresh result. Refresh preserves the selection epoch while replacing generation. If the response is lost after possible consumption, recovery must mark the selected session as requiring fresh login; it must not replay a consumed refresh token or fall back to a key/payment. A remote family whose replacement refresh token was lost cannot be claimed retired without a receipt. This is an API507 integration requirement, not implemented renewal behavior.

## Verification and release gates

Synthetic tests cover four login starting states, B versus environment A, fresh proofs/nonces, polling denial/expiry/backoff, secret-free machine events, chunk integrity, oversized bundles, selected-credential payment denial, manual payment compatibility, offline diagnostics, wallet preservation, real-child concurrent choices and deterministic SIGKILL barriers around store and pointer commits. Tests inject an isolated store through a code interface; no production environment variable enables plaintext test storage.

The previous external Mac keyring proof was a synthetic 2,000-byte cross-process roundtrip with cleanup. The external lock proof covered process contention, a paused owner and SIGKILL release on one macOS arm64 host. Neither proves Windows/Linux, locked store, reboot, SSH, power loss or full CLI acceptance. New native probe results must retain those distinctions. In this writer sandbox, the 11,580-byte synthetic bundle probe was blocked by Keychain `UNIX[Operation not permitted]`; dedicated-entry absence was confirmed afterward. This is a failed native roundtrip, not platform acceptance. The proposed portability CI runs real native file locks with an injected synthetic store; Windows skips the POSIX-only SIGSTOP observation. The workflow is retained outside this draft because the writer App token lacks workflow permission; it is not installed or reported green.

Before any supported cohort: record concrete OS/architecture/Node versions; test native package install, exact bundle bytes and chunking, store unavailable/locked/cancelled, restart/logoff/reboot, remote-terminal access, process-death locking and atomic replacement. The Windows byte limit is [documented by Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw); the binding's [pinned source](https://github.com/Brooooooklyn/keyring-node/tree/1635ed458e8349ba28233728a8238ad99a5b2817) passes byte slices. Published native provenance and platform execution still need verification.

Before ticket acceptance: use a controlled staging account for real browser approval, free account validation with environment A/candidate B, zero-credit and zero-debit evidence, restart, logout and measured revocation propagation. Deployment must demonstrate that every serving instance enforces the same revocation contract, its clocks and cached source ages stay within the configured bounds, and retirement records remain available for the lifetime of issued access. Passing source tests alone cannot establish these properties. No funded request is needed for API506.

The major changeset reflects the plain-login script break. Proposed delivery is a dedicated prerelease branch and version such as `2.0.0-browser-login.N`, opt-in dist-tag `browser-login`. No temporary public flag is added. This draft does not enter Changesets prerelease mode, change publishing credentials, publish, merge or modify the API505 flag. The existing main workflow can publish stable releases; do not merge there before API508 promotion approval.

Cohort instructions must name a concrete published version before use. Once a version exists, install it explicitly with `npm install -g nansen-cli@<cohort-version>`. Before rollback, run that new version's logout and inspect its cleanup result, then install the previously recorded stable version with `npm install -g nansen-cli@<prior-stable-version>`. Never restore a deleted key as rollback. Older CLI versions do not understand the session format or participate in its lock, so concurrent old/new writers are unsupported.

## Offline recovery without native locking

The lock binding is required for every saved-auth writer, including legacy key replacement and logout. An installation that omits optional dependencies cannot perform these mutations. musl/Alpine and architectures without a verified working native binding are not admitted to this browser-login cohort. Environment/explicit API-key requests, help and offline diagnostics still work. Restore the pinned optional dependencies in a supported installation before session cleanup. We intentionally retain one native lock protocol: a separate lockfile fallback would not exclude a native-lock owner. This leaves the legacy-write compatibility concern open for independent review rather than claiming it solved on unsupported installations.

For emergency removal of a **legacy saved API key only**, first stop every CLI/auth process, including older CLI versions. Back up config.json securely without displaying its contents. In `~/.nansen/config.json`, remove only `apiKey` and replace `auth` with `{"version":1,"selectionEpoch":"<fresh UUID>","active":{"kind":"none"}}`. Generate the UUID with `node -e 'console.log(require("node:crypto").randomUUID())'`; it is not a secret. Preserve every other config field, file permissions and all wallet files. Do not modify a config whose `auth.active.kind` is `session`: restore native locking instead so its generation remains available for retirement. Do not delete `auth-operations`, lock files or OS credential entries. This offline edit removes saved-key selection only; it does not revoke an API key or remove an environment override. Once native support is restored, rerun `nansen logout` to drain pending cleanup. The packaged copy of this document is available under `docs/browser-login.md` in the installed package.

Recovery processes at most eight journals per invocation, including directories left over the old admission limit. Logout commits its tombstone even when cleanup cannot finish; repeat it after unlocking storage until pending cleanup is drained. Active generations and live attempt locks remain protected. A durable unissued marker is cleared before the first token poll. Denial/expiry with no ambiguous poll response can be classified as unissued; a missing manifest alone cannot. In-memory candidate retirement receipts are retained for that cleanup report. Crash windows and lost responses remain uncertain.

A session missing the supported revocation-version claim now reports a possible cohort setup problem rather than prescribing repeated pairing. Operators must verify issuer `SESSION_ACCESS_REVOCATION_ENABLED` and API `BROWSER_SESSION_ACCOUNT_ENABLED`; a local unverified claim cannot establish the actual flag settings. The flags gate complete-family revocation coverage and free account validation respectively. Server admission and account/endpoint authorization remain separate. Unknown revoke receipts, including hypothetical `access_tokens_revoked:true`, remain unconfirmed: the pinned contract supports recorded/pending propagation or legacy refresh-only retirement, not that immediate-revocation promise.

At CLI `83d6f5d1e851e9da1f46902e3df93dd523bddedd`, root measured the actual native Mac state/store path with an 11,416-byte synthetic bundle: one read 798 ms, four concurrent reads 2,956 ms, sixteen 11,764 ms. Separate instances share the module-level directory queue. Security measured an 11,134-byte, six-chunk synthetic executor: mean read 474 ms, write 942 ms, remove 1,332 ms, single operation 69 ms. These are different backends and sizes; neither yields a before/after ratio or a measured cross-process concurrency threshold. Reviewer A's earlier 136/607/2,466 ms measurements had unspecified bundle size and preceded the guardian repair. Latency/cohort acceptance is required before promotion. This repair intentionally adds no token cache, shared-lock protocol or batching redesign.

### Helper lifetime repair and evidence

The previous helper had only a parent-side timer. A deterministic synthetic backend probe at `b907aff` proved that parent SIGKILL could let logout delete the final journal before an orphan recreated a secret chunk. The new handshake grants authority only after helper-owned execution exclusion. Parent loss before the handshake cannot grant a late child permission to write; parent loss during native execution either kills the whole helper or leaves exclusion held until actual termination. API507 must use the same `createAuthState`/`createAuthStore` boundary and retain `auth-store.lock`; it must not bypass it with direct native writes or a second owner.

The pinned lock source uses `flock` on macOS, `F_OFD_SETLK` on Linux and `LockFileEx` on Windows. Each helper opens and locks its own descriptor; this design does not rely on inherited ownership behaving alike. [Node documents unconditional SIGKILL termination](https://nodejs.org/api/process.html#signal-events), and [Worker exit follows thread termination](https://nodejs.org/api/worker_threads.html#event-exit). The watchdog uses whole-process termination, not `worker.terminate()` or a timer inside the blocked executor. [Windows may delay lock release after process termination](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex); lock refusal must remain an incomplete-cleanup outcome, never assumed success. Native Windows execution still needs verification.

Root reran the actual guardian/thread/store at **83d6f5d1e851e9da1f46902e3df93dd523bddedd**. Native macOS arm64 passed an 11,416-byte owned synthetic bundle preflight, roundtrip and deletion. Debian 12 x64, Node 22.23.2, temporary isolated GNOME Secret Service 42.1 passed an 11,455-byte stored bundle, daemon restart read and bounded namespace deletion. Actual locked collection preflight refused in 128 ms; unlock preserved the bundle, and deletion passed. Temporary directories were removed. These are current guardian-boundary proofs at the named head, superseding the older b907-only qualification; this repair leaves those native source files unchanged. They establish neither public login/staging nor Windows, desktop cancellation, OS login/PAM or reboot persistence.

Physical deletion remains best effort: `local: removed` records successful bounded delete/readback, not proof that an external credential daemon has cancelled every outstanding write after client death. An already dispatched securityd/Secret Service operation could finish after client termination. Synthetic executor tests prove helper exclusion and lifetime, not daemon cancellation. Native acceptance must resolve this outstanding-write gap before promotion; do not infer all secret bytes are irrevocably erased from a killed helper alone.

The Linux helper continues to forward the canonical D-Bus/session-runtime variables. The suggestion to add DISPLAY/WAYLAND_DISPLAY was hypothetical; the isolated Secret Service evidence does not require them or prove graphical prompt behavior. The environment allowlist remains narrow pending an actual desktop failure or platform requirement.

## Damaged or unrecognized journals

Admission, recovery and pending counts recognize the same UUID-shaped `.json` journal names. Other JSON files are preserved, reported as unrecognized, and do not consume the eight-operation admission limit. Other unknown files are also left untouched. A recognized but malformed/unreadable journal stops recovery with `AUTH_JOURNAL_INVALID` naming `auth-operations`; parsing never prints its contents. Logout may already have cleared selection, but reports incomplete cleanup with that code. This is not evidence that the retained generations were removed.

Do not delete, rename away or quarantine these files merely to make login succeed: they may be the only record of a generation needing retirement/deletion. Stop all CLI/auth processes and retain the directory, config and secure-store entries. If a known-valid backup for the same operation and current state exists, restore only that journal while preserving ownership and permissions. Otherwise ask support/operator engineering to reconcile the retained generation IDs and current pointer before any repair; do not send credential-bearing files or store contents in public reports. Automatic reconstruction or blanket deletion is not supported. After a validated restoration, run logout to process at most eight recognized journals and inspect every cleanup result; escalate if it remains invalid.

Live cancellation before the first token request, or after known pending/slow-down responses with no earlier ambiguity, can report no issued session. Any earlier network/5xx/unknown response, an in-flight request, lost response or process crash retains uncertainty. The durable marker is written before the first poll; subsequent already-durable calls avoid the global queue/lock. That optimization never clears the on-disk marker after pending. Auth telemetry uses only `/login` or `/logout`, allowed flag names and bounded error categories; positional codes, option values, arbitrary flag names and chain/hostname metadata are excluded from both success and failure.

Trading quote, signed-transaction submission and bridge-status calls to `trading-api.nansen.ai` retain their existing credential-free transport. Limit orders retain their separately wallet-signed challenge/JWT flow; the existing optional environment `X-API-Key` header is not a browser-session export. No browser bearer is forwarded to that separate audience. Pasting a saved API key did not replace those wallet authorization requirements either. MCP install similarly provisions a separate integration key rather than reusing browser session custody.

## Review follow-up

Login chooses NDJSON from stdout's terminal state. Redirecting stdout keeps machine output even when stdin remains interactive; `--human` prompts depend on stdin. Blank environment keys do not suppress that prompt.

A selected API key receives the server's manual payment requirements on 402 without automatic signing or retries. Browser sessions never receive payment fallback. Hosted simulation rejects 401/403 for both selected keys and sessions; this preserves account, region and sanctions denials before signing. Anonymous simulation retains its existing outage policy.

Missing or unloadable native keyring bindings now produce reinstall guidance after the helper exits. This does not certify native support: offline diagnostics still avoid opening the store or triggering an OS prompt. Every request currently reads its selected generation under the authentication lock. Native-read latency remains a required cohort acceptance check; a cache must not bypass local logout or account replacement.
