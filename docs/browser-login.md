## Commands and selection

Plain `nansen login` always requests fresh approval, including when an environment key or saved credential exists. `--no-browser` skips automatic opening only. Email/password and Google are the upstream consent methods; Apple is not advertised. The browser owns explicit account/client/code/access consent. Visiting the URL alone does not approve.

Ordinary commands select an existing supported explicit override, then NANSEN_API_KEY, then one saved credential. There is no new global key option and no named profile. An empty selected key is an error. Saved authentication can be a legacy key or browser session. The new `config.json.auth` pointer also represents a deliberate logout, so an old development config key cannot silently reappear. Existing direct API-key commands continue to work. Legacy explicit `--human`/`--api-key` setup retains option, environment, then hidden-prompt precedence. Plain login no longer copies an environment key to config.

Candidate B is checked independently through GET `/api/v1/account` with only its Bearer token. Environment A cannot mask a rejected B. This check is free and permits zero research credits. An environment override remains in force after B is saved; unset it to use B. Data commands never launch consent. Selected sessions renew under the shared owner within 60 seconds of access expiry or after expiry. An outage never changes accounts automatically. Failures without proven safe retry evidence can require new pairing, as described below.

Selected credentials never trigger automatic x402 signing. Anonymous automatic payment and explicit manual Payment-Signature with an API key retain their existing behavior. Browser Bearer requests cannot include an API key or payment signature. The resource contract uses Bearer without DPoP; a copied valid access token is accepted by that policy. Proof of key possession applies to authorize/poll/refresh/revoke, not API requests. Only the 58 explicitly admitted stable-v1 research method/path pairs can become available when account and research admission are enabled. Execution remains excluded even then. MCP installation requires a conventional API key, and trading/RPC paths never receive the browser token.

## Starting states and supported scope

| Starting state | Plain login | Ordinary commands after success |
| --- | --- | --- |
| No credentials | Fresh approval installs B | B |
| Environment key A only | Verify B independently, save B, report override | A until the key is unset, then B |
| Saved key A | Fresh approval replaces A after durable install | B; failed approval/install preserves A |
| Saved session A | Fresh approval installs B and retires A | B; failed approval/install preserves A |
| Environment A and saved B | Fresh approval is independent of A | A still wins; status distinguishes saved and effective |
| Missing/locked store | Fail before approval with recovery guidance | Existing direct API-key access remains usable |

A selected invalid key never falls back to a session, another account or payment. Login checks the approved account for free even at zero credits; paid research then checks that effective account's credits and entitlements. Successful retries can charge again. Login does not purchase credits or create a subscription. Existing server auto-topup configuration is separate from CLI payment fallback.

## Machine output

`login --json` and non-TTY login emit NDJSON. There is one pending event and one terminal event on a normal approval attempt. Preflight failure emits only the terminal error. Human progress goes to stderr in machine mode.

```json
{"version":1,"event":"pending","verification_uri":"https://idp.nansen.ai/device?user_code=ABCD-EFGH","user_code":"ABCD-EFGH","expires_at":"2026-09-19T00:10:00.000Z"}
{"version":1,"event":"saved","account_id":"example-account","effective_source":"session","cleanup":[]}
```

Failure/cancellation events contain a fixed code, message and cleanup outcomes. Events never contain device_code, access/refresh token, private JWK, proof or nonce. Public user codes are displayed only for approval, never telemetry. Local diagnostics are cached/unverified; the native store is not opened by status because it could prompt. `storage_access:not_checked_no_prompt` is deliberate, not a success claim.

## Custody and coordination

Optional, pinned dependencies are `@napi-rs/keyring@2.1.0` and `fs-native-extensions@1.5.1`. Help, offline metadata and environment/explicit API-key requests do not need native bindings. Saving/removing auth requires the lock binding; browser pairing also requires secure storage. Reinstall with optional dependencies if a binding is absent. No plaintext, wallet-password-file or Linux keyutils fallback exists.

The browser session's private ES256 JWK, refresh token and access cache live only in `nansen-cli-api-auth-v1` OS entries. Native operations run in bounded child processes; secret input/output travels through private pipes. Helpers receive no secret argv or inherited API-key environment. Before receiving operation or credential data, the helper independently acquires the stable `auth-store.lock` execution gate inside the same authentication directory. Every read/delete uses this same gate, so recovery cannot overtake a helper whose parent died. The gate is subordinate to the existing auth-state owner, not an alternate writer protocol; it is never unlinked. Successful operations await helper termination before releasing a writer's lock. If termination is not observed within one second of the ten-second kill deadline, the caller fails instead of waiting indefinitely; the helper-owned gate still protects cleanup, which must retain the journal if the helper survives. Synchronous keyring calls execute on a worker thread inside that guarded process. Its main thread keeps the parent pipe open and force-terminates the entire process on parent EOF or its own ten-second watchdog, including when the native thread is blocked. A result is returned only after that thread exits. An externally stopped process cannot run its watchdog, but retains exclusion: recovery fails bounded, reports deletion incomplete and retains its journal until that process dies. No age-based lock stealing or blind cleanup success is allowed. The CLI uses ordinary Entry construction, not the Windows withTarget constructor that can create an empty placeholder.

The UTF-8 bundle has an explicit 16 KiB client compatibility limit. It is split into at most eight 2,048-byte entries plus a bounded manifest with byte length, chunk count and SHA-256 digest. The manifest and every chunk belong to one immutable random generation. This respects the documented Windows 2,560-byte blob limit using the binding's byte setter, without assuming an entire JWT/key bundle fits one entry. Missing/mixed/corrupt chunks fail closed. Runtime byte length and readback are checked before selection. Larger issuance fails without replacing the prior credential.

Linux explicitly selects persistent Secret Service over the user's D-Bus session. macOS uses Keychain. Windows uses Credential Manager with the binding's default Enterprise persistence, which can roam according to OS policy; it is not promised device-local-only. Windows cohort support still requires native verification and any required Local-persistence adapter. Remote shells need a usable unlocked store; a kernel keyring or a headless process without Secret Service is not an equivalent fallback.

A stable, never-replaced `auth.lock` uses an OS advisory lock and same-process serialization. No lock is stolen because of its age. Only local filesystems are intended; network/synchronized home directories are unverified. Login snapshots selectionEpoch before approval, releases the global lock while waiting, then compares that epoch before installation. Login/key replacement/logout changes the epoch; refresh changes only secret generation. An earlier pending login cannot overwrite a later committed choice or logout.

All saved-auth writes use auth-state. The same-directory atomic config replacement preserves unrelated settings, removes a superseded saved key, and selects a complete secure generation. Legacy explicit API keys retain their existing config-file storage policy. Nonsecret bounded journals list only operation/generation IDs for targeted recovery, never credentials. Live attempts hold separate OS locks. Recovery skips active generations and live attempts, cleans interrupted unreachable generations, and never restores a superseded credential. A lost commit acknowledgement rereads the pointer before cleanup. If the pointer cannot be classified safely, leave cleanup pending rather than revoke a possibly active session.

Process interruption and filesystem power loss differ. Unit/child tests demonstrate process-fault recovery under the tested filesystem semantics. Native storage readback and POSIX file/directory fsync do not prove all-OS power-loss durability. Windows replacement/durability, store blocking behavior and cross-login persistence remain verification gates.

## Logout and uncertainty

Logout advances the epoch and leaves a tombstone before retiring/deleting the prior session. It preserves wallets, wallet password entries and environment keys. A locked store can permit clearing selection but prevent physical deletion; the CLI reports deletion incomplete. Unlock the OS store and rerun logout. Successful local deletion with offline/rejected retirement is reported separately as remote revocation unconfirmed. Contact the session/revocation operator to revoke the affected session if cleanup cannot be confirmed; no supported self-service control is established here.

`POST /token/revoke` uses the old refresh token and its own key, without requiring live access. A protected receipt means family retirement recorded with API propagation pending; it is not immediate gateway rejection. The consumer separately bounds cached revocation data by both receipt age and source age, with explicitly configured age plus future-skew bounded by the configured stale window and 300 seconds. Those are engineering ceilings, not an accepted deployment propagation policy; the CLI does not turn a receipt into an immediate-rejection or fixed-delay promise. A legacy refresh-only receipt means already-issued access can survive until expiry; it is reported truthfully but does not meet the required rollout behavior. Before rollout, logout/revocation must invalidate all original, rotated and copied access tokens from that browser session while leaving other sessions, replacement accounts and independent API keys unaffected. Live measured propagation, restart/outage behavior, durable revocation records and feed/anchor retention are still required. Neither offline/unconfirmed cleanup nor natural JWT expiry satisfies this requirement. No instantaneous invalidation or particular propagation interval is claimed. Other devices and independently managed API keys are not revoked.

There is an unavoidable crash window after issuance but before durable custody. A lost issuance response or killed process can leave a family for which this CLI lacks cleanup authority. Device codes are single-use; replay is not a recovery protocol. Pre-issuance cancellation stops polling and allows the grant to expire, since there is no CLI cancel endpoint. API507 records a typed nonsecret rotation journal before sending `/token/refresh`. A complete replacement already stored can be recovered after interruption; otherwise the command reports renewal uncertainty and requires fresh login. Replay grace does not return the replacement token, and replay outside grace can retire the family. The CLI never retries an uncertain token.

## Automatic session renewal

Each command selects its credential first. Explicit/environment keys bypass inactive saved sessions, including uncertain or expired ones. A selected session is read under the same native owner on every request; no secret cache is introduced. Waiting commands accept the current generation within their unchanged selection epoch. A concurrent login/logout changes the epoch and defeats stale installs.

Refresh uses the original private key, exact saved issuer/API audience, fresh DPoP proof/nonce and JSON `/token/refresh` body. No ambient key, cookie or payment is sent. The replacement response has no top-level scope; the saved read scope and new JWT bindings must agree. Resource API requests remain Bearer-only. There is no automatic refresh loop on a resource 401 and no browser prompt from a data command. Direct resource retries reacquire credentials after backoff; an SSE stream renews before opening and is never replayed for renewal.

The first attempted rotation upgrades config.auth to version 2 before dispatch, even if connection establishment fails or the issuer refuses without consuming the token. It does so without changing selectionEpoch. OS bundle/chunk format stays v1. Typed rotation journals use the epoch as their operation ID and hold at most source/target generation IDs. Supported phases are in_flight, ready, blocked, retryable and retired. The retired phase stores only a fixed remote outcome so interrupted physical deletion can finish without losing cleanup authority. Old independent-family journals retain their original meaning. Older API506 code rejects the v2 pointer and cannot interpret typed journals as permission to revoke a still-active family. Never manually downgrade this metadata. Logout retains v2 metadata, so it does not make a pre-v2 binary safe. Recovery requires a tested v2-compatible version; no supported in-place pre-v2 downgrade is evidenced. Do not force a pointer version, delete journals or restore a superseded key. Older writers are unsupported concurrently.

Same-family rotation recovery deletes obsolete refresh generations locally, with no remote retirement. Before renewal, ordinary data commands can also discharge pre-existing pairing journals for separate orphaned families; that recovery may call /token/revoke using the retained family authority. It is bounded by the owned operation signal and transport deadline. Turning this into a no-op could discard avoidable remote cleanup. No caller-supplied resource-request cancellation contract is added here. Actual logout/replacement first changes selection, then retires only the displaced family using its newest complete or retained parent bundle. A consumed parent still identifies its family while the server retains its row. A pruned parent cannot establish remote cleanup. Physical deletion and recorded/pending remote retirement remain separate outcomes. One unresolved rotation per epoch and at most eight admitted journals prevent an unbounded generation chain; incomplete old-generation cleanup must finish before another rotation.

A known non-consuming nonce challenge retries once with a fresh proof. A documented rate-limit/proof refusal preserves retryable state and returns a bounded error; a later command can use old access only before expiry. A 401 invalid_refresh_token requires login. A lost/truncated response, unknown error body, malformed success, post-dispatch cancellation or 5xx is uncertain because it cannot prove the token was not consumed. No expired access, old API-key restoration or hidden payment is allowed. If storage fails after rotation, retry the command to recover a fully stored target. If no complete target exists, log in again. Inaccessible storage remains a storage error, not proof that the target is absent.

The queue plus native lock wait is bounded to 15 seconds. Each owned operation has a 60-second abort budget shared by recovery and native calls; refresh transport including nonce/body has a 20-second limit. Each existing native guardian also retains its independent 10-second watchdog. Aborted native work is awaited, with the guardian's one-second unobserved-termination failure bound and persistent exclusion still enforced. These are client failure limits, not a platform SLA or a promise that a paused/unkillable process physically terminates on time. No timeout steals a lock or permits a late write. Sustained contention may return AUTH_BUSY. Filesystem power loss and blocked OS syscalls remain separate platform limits.

Offline `auth status` adds `saved_session.renewal_state`: not_recorded, pending_or_uncertain, ready_local_recovery, retryable, login_required or metadata_unreadable. It reads bounded nonsecret metadata only. Pending cannot distinguish an active owner from a crashed one. `cached_unverified` and `not_checked_no_prompt` remain accurate; status neither opens secure storage nor refreshes/revokes a session. Tokens, proofs, nonce and private keys are excluded from status, journals and errors.

## Offline recovery without native locking

The lock binding is required for every saved-auth writer, including legacy key replacement and logout. An installation that omits optional dependencies cannot perform these mutations. musl/Alpine and architectures without a verified working native binding are not admitted to this browser-login cohort. Environment/explicit API-key requests, help and offline diagnostics still work. Restore the pinned optional dependencies in a supported installation before session cleanup. We intentionally retain one native lock protocol: a separate lockfile fallback would not exclude a native-lock owner. This leaves the legacy-write compatibility concern open for independent review rather than claiming it solved on unsupported installations.

For emergency removal of a **legacy saved API key only**, first stop every CLI/auth process, including older CLI versions. If any pending, corrupt or unrecognized auth-operations journal exists, stop and use a compatible recovery binary or support-assisted reconciliation instead. Back up config.json securely without displaying its contents. In `~/.nansen/config.json`, remove only `apiKey` and replace `auth` with `{"version":1,"selectionEpoch":"<fresh UUID>","active":{"kind":"none"}}`. If the existing auth version is 2, retain version 2 in this legacy-key-only tombstone; do not downgrade it. Generate the UUID with `node -e 'console.log(require("node:crypto").randomUUID())'`; it is not a secret. Preserve every other config field, file permissions and all wallet files. Do not modify a config whose `auth.active.kind` is `session`: restore native locking instead so its generation remains available for retirement. Do not delete `auth-operations`, lock files or OS credential entries. This offline edit removes saved-key selection only; it does not revoke an API key or remove an environment override. Once native support is restored, rerun `nansen logout` to drain pending cleanup. The packaged copy of this document is available under `docs/browser-login.md` in the installed package.

Recovery processes at most eight journals per invocation, including directories left over the old admission limit. Logout commits its tombstone even when cleanup cannot finish; For a locked store, repeat it after unlocking until pending cleanup is drained. Damaged journals or a pointer/journal disagreement instead require operator reconciliation; unlocking alone cannot repair metadata. Active generations and live attempt locks remain protected. A durable unissued marker is cleared before the first token poll. Denial/expiry with no ambiguous poll response can be classified as unissued; a missing manifest alone cannot. In-memory candidate retirement receipts are retained for that cleanup report. Crash windows and lost responses remain uncertain.

A session missing the supported revocation-version claim now reports a possible cohort setup problem rather than prescribing repeated pairing. Operators must verify issuer `SESSION_ACCESS_REVOCATION_ENABLED` and API `BROWSER_SESSION_ACCOUNT_ENABLED`; a local unverified claim cannot establish the actual flag settings. ### Helper lifetime repair and evidence

The previous helper had only a parent-side timer. A deterministic synthetic backend probe at `b907aff` proved that parent SIGKILL could let logout delete the final journal before an orphan recreated a secret chunk. The new handshake grants authority only after helper-owned execution exclusion. Parent loss before the handshake cannot grant a late child permission to write; parent loss during native execution either kills the whole helper or leaves exclusion held until actual termination. API507 must use the same `createAuthState`/`createAuthStore` boundary and retain `auth-store.lock`; it must not bypass it with direct native writes or a second owner.

The pinned lock source uses `flock` on macOS, `F_OFD_SETLK` on Linux and `LockFileEx` on Windows. Each helper opens and locks its own descriptor; this design does not rely on inherited ownership behaving alike. [Node documents unconditional SIGKILL termination](https://nodejs.org/api/process.html#signal-events), and [Worker exit follows thread termination](https://nodejs.org/api/worker_threads.html#event-exit). The watchdog uses whole-process termination, not `worker.terminate()` or a timer inside the blocked executor. [Windows may delay lock release after process termination](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex); lock refusal must remain an incomplete-cleanup outcome, never assumed success. Native Windows execution still needs verification.

Root reran the actual guardian/thread/store at **83d6f5d1e851e9da1f46902e3df93dd523bddedd**. Native macOS arm64 passed an 11,416-byte owned synthetic bundle preflight, roundtrip and deletion. Debian 12 x64, Node 22.23.2, temporary isolated GNOME Secret Service 42.1 passed an 11,455-byte stored bundle, daemon restart read and bounded namespace deletion. Actual locked collection preflight refused in 128 ms; unlock preserved the bundle, and deletion passed. Temporary directories were removed. These are current guardian-boundary proofs at the named head, superseding the older b907-only qualification; API506 final repair leaves those native source files unchanged. API507 adds dispatcher cancellation, so this older run alone is not proof of its complete renewal path. They establish neither public login/staging nor Windows, desktop cancellation, OS login/PAM or reboot persistence.

Physical deletion remains best effort: `local: removed` records successful bounded delete/readback, not proof that an external credential daemon has cancelled every outstanding write after client death. An already dispatched securityd/Secret Service operation could finish after client termination. Synthetic executor tests prove helper exclusion and lifetime, not daemon cancellation. Native acceptance must resolve this outstanding-write gap before promotion; do not infer all secret bytes are irrevocably erased from a killed helper alone.

The Linux helper continues to forward the canonical D-Bus/session-runtime variables. The suggestion to add DISPLAY/WAYLAND_DISPLAY was hypothetical; the isolated Secret Service evidence does not require them or prove graphical prompt behavior. The environment allowlist remains narrow pending an actual desktop failure or platform requirement.

## Damaged or unrecognized journals

Admission, recovery and pending counts recognize the same UUID-shaped `.json` journal names. Other JSON files are preserved, reported as unrecognized, and do not consume the eight-operation admission limit. Other unknown files are also left untouched. A recognized but malformed/unreadable journal stops recovery with `AUTH_JOURNAL_INVALID` naming `auth-operations`; parsing never prints its contents. Logout may already have cleared selection, but reports incomplete cleanup with that code. This is not evidence that the retained generations were removed.

Do not delete, rename away or quarantine these files merely to make login succeed: they may be the only record of a generation needing retirement/deletion. Stop all CLI/auth processes and retain the directory, config and secure-store entries. If a known-valid backup for the same operation and current state exists, restore only that journal while preserving ownership and permissions. Otherwise ask support/operator engineering to reconcile the retained generation IDs and current pointer before any repair; do not send credential-bearing files or store contents in public reports. Automatic reconstruction or blanket deletion is not supported. After a validated restoration, run logout to process at most eight recognized journals and inspect every cleanup result; escalate if it remains invalid.

Live cancellation before the first token request, or after known pending/slow-down responses with no earlier ambiguity, can report no issued session. Any earlier network/5xx/unknown response, an in-flight request, lost response or process crash retains uncertainty. The durable marker is written before the first poll; subsequent already-durable calls avoid the global queue/lock. That optimization never clears the on-disk marker after pending. Auth telemetry uses only `/login` or `/logout`, allowed flag names and bounded error categories; positional codes, option values, arbitrary flag names and chain/hostname metadata are excluded from both success and failure.

The API506 A3 native-lock legacy-write compatibility disagreement remains open. A6 latency redesign remains deferred; no credentials are cached to avoid native reads. API507 still requires authorized free-account staging renewal/revocation, measured propagation, server deployment gates and API508 promotion. Its stacked draft targets the API506 branch; current CI filters PR targets to main, so absent stacked CI is not a pass and does not justify changing the base or workflows.
